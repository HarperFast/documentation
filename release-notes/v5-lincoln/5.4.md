# 5.4 Release Notes

### Patch Releases

All patch release notes for 5.4.x are available on the [releases page](https://github.com/HarperFast/harper/releases?q=v5.4&expanded=true).

## Upgrade Notes

Full-text indexes using fulltext 0.5.0 with current field-based declarations, or prerelease 0.6, rebuild locally after this upgrade. Plan for search unavailability and review the [Tantivy upgrade requirements](#tantivy-027-and-existing-index-rebuilds) before deploying; direct downgrade to fulltext 0.5.x is unsupported.

## Nested Relationship Constraints

[Honor nested relationship filters and pagination](https://github.com/HarperFast/harper/pull/3279) and [Fix wrong rows, unfiltered selects and ignored sorts in relationship queries](https://github.com/HarperFast/harper/pull/3775) correct REST and programmatic relationship queries that accepted nested constraints, non-leading relationship conditions, or top-level relationship sorts without applying them completely. Filters, ordering, offset, and limit inside `select` apply per parent in collection and single-record reads, and parents remain present when the nested selection has no matches. Outer relationship filters — whether they lead the query or follow another condition — constrain the selected children as well as the parents, so an identical filter does not need to be repeated inside the nested selection. When a top-level sort across a to-many relationship (such as `sort(products.name)`) runs in memory — when the target attribute is not `@indexed`, a more selective condition on another attribute leads the query, or `enforceExecutionOrder: true` is set — Harper now orders matched parent records by the list of each parent's related values in relationship order, compared element by element, instead of ignoring the sort; when an `@indexed` target attribute leads the query, Harper continues to order via the related table's index join.

**Upgrade impact:** requests using nested constraints can return fewer children, and requests with top-level sorts across to-many relationships now return parents ordered by their related values. Unsupported filters on plain JSON projections or custom non-table resources, and nested full-text predicates, now return HTTP 400 instead of being ignored. Sorting and pagination of plain JSON arrays remain supported. Nested selections on source-backed caches use the same local-entry eligibility and ordering rules as a top-level query; the correction now applies those rules to constrained nested results. Refreshed nonmatches are excluded from the returned child page, so cache-backed child arrays can also shrink. See [Filtering and Paging Each Relationship](/reference/v5/rest/querying#filtering-and-paging-each-relationship) and [`sort`](/reference/v5/resources/resource-api#sort).

These corrections are not released yet.

## Replication

### Dedicated Replication Threads

`replication.threads` (default `0`) starts worker threads that run replication only. They own the replication port and every subscription, so a peer catching up no longer competes with application requests. These threads load no application code, which limits applications that use `setResidencyById` or `setComputedAttribute` on indexed attributes. See [Dedicated Replication Threads](/reference/v5/replication/overview#dedicated-replication-threads).

### Local Replicas of Records Fetched From Another Node

On RocksDB, a table sharded with `setResidency` lets a node that reads a record it does not hold keep the fetched record as a local replica instead of moving it. The replica is served locally until an owner writes the record or its lifetime passes, set by the new `@table` arguments [`replicaExpiration` and `replicaRefreshFraction`](/reference/v5/database/schema#replicaexpiration-and-replicarefreshfraction) (default one hour, renewed by reads after half of it). Local replicas are RocksDB-only; LMDB continues to proxy remote reads without storing replicas or running a replica sweep.

## Subscriptions

### Resuming a Subscription From a Checked Position

A `subscribe` request can now carry the `databaseGeneration` its position came from. Harper then checks the position before and during the replay, and refuses one whose history was replaced (`DatabaseGenerationChangedError`, status code 409) or pruned (`ResumeHistoryUnavailableError`, status code 410) instead of replaying what is left. The subscription's `resumeVerified` promise resolves `true` once the replay is complete and checked. Requests without the field behave as before, and the check applies to RocksDB databases only. See [Resuming from a position](/reference/v5/resources/resource-api#resuming-from-a-position).

### Durable MQTT Sessions No Longer Replay Short

A durable MQTT session now resumes through the same checked replay. When a reconnect's saved position names history that audit retention has removed, Harper deletes the session and reports `sessionPresent: false` (or, if the problem appears after `CONNACK`, sends an MQTT v5 `DISCONNECT` with reason code `0x83` and closes the connection) instead of delivering a partial catch-up. A position saved before a restore or copy, or on another cluster node, resumes best-effort, as before. A quiet topic's position is kept current, so retention on other tables does not reset it, and positions no longer skip unacknowledged messages that share a transaction. Resubscribing to a topic the session already holds continues from its saved position, and QoS 0 subscriptions are kept with the session and resume live. Each connection's Last Will is kept separately, so a connection that is taken over publishes its own will, never the newer connection's. See [Durable Sessions](/reference/v5/mqtt/overview#durable-sessions).

## Built-in Agent

### Turning Off or Host-Limiting `http_fetch`

`agent.httpFetch` sets whether the built-in agent has its `http_fetch` tool: `false` removes it, and `{ allow: [...] }` refuses any request whose host is not on the list. It is read at startup only, and `set_agent_config` rejects it. `http_fetch` now also checks every redirect hop before following it, in every mode. See [Restricting `http_fetch`](/reference/v5/configuration/options#restricting-http_fetch).

### Cut-Off Agent Replies End the Run `error`

A model reply that did not finish now ends the agent session `error`, with the reason in `lastError`, instead of `completed`. That covers a reply cut off at the output-token cap or at the model's context window, one stopped by a content filter or a refusal, one that asks for tool calls of which none could be parsed, and an empty reply. Nothing from that reply reaches the transcript, and its tool calls are neither run nor queued for approval. Its usage is still kept on the session, and counts toward the agent's spend caps. The new `agent.maxTokens` (default `16384`) is sent with every model request the agent makes; lower it for a model whose own output limit is smaller, or the provider rejects each request. See [`agent`](/reference/v5/configuration/options#agent) and [Agent](/reference/v5/operations-api/operations#agent).

### The `config` Scope Is the Config File

The built-in agent's read-only `config` filesystem scope used to be the directory holding `harper-config.yaml`. On a default install that is `rootPath`, so the agent could read `keys/`, `ssh/`, and the raw database files. It is now the config file alone. The new `agent.configScope` replaces it at startup with another file or directory, which keeps the config file readable only if it contains it. In every scope, the agent's filesystem tools now refuse to read Harper's key directories (`<rootPath>/keys` and `<rootPath>/ssh`), files named `*.pem`, `*.key`, or `.jwtPass`, and text holding a PEM private key, and they refuse to write into the key directories. `set_agent_config` now rejects `configScope` and `componentsScope` with a `400`, as it already did `httpFetch`. An agent that read other files through `config` needs `configScope` set to a directory that holds them. See [Filesystem scopes](/reference/v5/configuration/options#filesystem-scopes) ([harper#3041](https://github.com/HarperFast/harper/issues/3041)).

### Credential Values Are Masked in the Agent's Config and Log Reads

The config file can hold plaintext credentials, such as a model `apiKey` passed through `HARPER_SET_CONFIG`, and the agent's `config` scope returned them, as did its `logs` scope and `read_log` for anything a component logged. The agent's reads of the `logs` and `config` scopes, and its `read_log` results, now show the value of every credential-named key (`apiKey`, `password`, `token`, `secret`, and similar) as `*`s, including a value that continues on more-indented YAML lines and a value a positional read starts in the middle of. `grep_files` searches the masked text in those scopes, and the agent's `read_log` refuses `filter`, which matches the unmasked log. The `components` scope, and `read_log` called through the operations API or an MCP client, are unchanged. Sessions recorded before this release keep whatever they already read, so rotate any credential an agent session may have read. See [Masked credential values](/reference/v5/configuration/options#masked-credential-values) ([harper#3097](https://github.com/HarperFast/harper/issues/3097)).

### Capped and Paged Agent Tool Results

The built-in agent added every tool result to its conversation in full, so one large result, such as a log read whole, could fill the model's context window and leave the session unusable. A tool result is now cut to `agent.maxToolResultBytes` (default `65536`) before it is stored, and `read_file` pages through a file by line, with no size limit, returning a cursor (`nextLine`, `nextOffset`) to continue from. When a provider still rejects a request as too long for the model, the agent cuts the most recent tool results to 2 KiB and retries once, and prompting a session left unusable by an earlier version usually recovers it the same way. The agent also stops sending its system prompt twice per request. See [When a conversation outgrows the model's context window](/reference/v5/operations-api/operations#when-a-conversation-outgrows-the-models-context-window).

### Spend Caps for the Built-in Agent

The agent records the usage of each model call on its session, and `get_agent_session` and `list_agent_sessions` report a session's totals as `usage`. Two caps bound a whole session, across every run in it: the new `agent.maxSessionTokens`, and `agent.maxCostUsd`, which is now enforced from model pricing and no longer defaults to `5.00`. A reply the agent rejects, such as one cut off at `agent.maxTokens`, still counts toward a cap, though it stays out of the transcript. A session at a cap makes no further model call: it ends `error`, or `completed` with `lastError` naming the cap when the call that reached it was the final answer. A cap that cannot be measured stops the session rather than letting it run uncapped. Caps count calls that return: a call that fails, even one the provider billed, is not counted. If your configuration already sets `agent.maxCostUsd`, declare `pricing` on the generative entry the agent uses, and start new sessions: a session created before 5.4.0 recorded no usage, so it cannot be continued under a cap. See [Agent spend caps](/reference/v5/configuration/options#agent-spend-caps).

### Agent Cancellation and Limits

`cancel_agent_run` now answers every pending approval with a `cancelled_by_operator` result in the same write that marks the session `aborted`, so an approved action that has not started never runs, then or on the session's next prompt, and the session stays `aborted` even when a run was mid-step. The 409s `agent_prompt` returns for a busy session or a cancel now carry a `code` and `retryable`, so a client can tell a prompt it may resend from one already saved, and `get_agent_session` and `list_agent_sessions` report `runInFlight`. `agent.maxTurns` is now validated as a positive integer at startup and by `set_agent_config`, where a value such as `null` used to make every later run end without a model call; a bare `maxTurns:` in the configuration file now fails the agent's start. See [`cancel_agent_run`](/reference/v5/operations-api/operations#cancel_agent_run).

## Models

### Model Pricing and Per-Call Cost

A `models.generative` entry can now declare `pricing: { inputPerMtok, outputPerMtok }`, what you pay in USD per million prompt and completion tokens. Harper ships no prices of its own. Each `generate()` call is priced at the rates of the entry that served it, a fallback included, and the result carries `costUsd` when that entry is priced and the provider reported both token counts. With `toolMode: 'auto'` it covers the final round, and streaming calls are not priced. This makes `maxCostUsd` work on `toolMode: 'auto'` calls; before, it had no prices behind it and never tripped. A `toolMode: 'auto'` round that leaves `maxCostUsd` or `maxToolTokens` unmeasurable, because the entry is unpriced or the provider reported no token counts, now stops the call with the budget error (429) instead of warning once and continuing, so set `pricing` on entries you cap by cost. See [Pricing](/reference/v5/models/overview#pricing).

### Truncating Long Embedding Inputs

`models.embed(input, { truncate: true })` cuts each input to what the embedding model accepts, keeping the start of the text and any task prefix, instead of failing on an input longer than the model's context window. Only a backend that can truncate serves such a call: Ollama, Bedrock Cohere embed v3 and v4, and OpenAI-compatible embedding entries that set the new `truncation: vllm` for a vLLM 0.18 or later endpoint. If no candidate can, the call fails before any request is sent. Calls without the option send the same requests as before. Custom backends declare the capability with `defineBackend({ truncate: true })`. The `@embed` directive and the `/v1/embeddings` endpoint do not expose the option yet. See [Truncating long inputs](/reference/v5/models/api#truncating-long-inputs).

## Memory

### Smaller Per-Thread Baseline

An idle Harper thread now uses roughly 40% less JavaScript heap (about 58 MB down to 35 MB in a default install, before any application code loads). Harper's compiled code is smaller in memory, and several dependencies used only by specific features (LMDB storage, certificate revocation checks, certificate generation, `system_information`) now load when that feature is first used.

Source maps are no longer enabled by default, so stack traces from Harper's core point at its compiled JavaScript. If you control the process environment (not on Fabric clusters that Harper hosts), set `NODE_OPTIONS=--enable-source-maps` to map them back to the TypeScript sources. See [Source Maps in Stack Traces](/reference/v5/configuration/debugging#source-maps-in-stack-traces).

## Component Deploys

### Certifying a Release in a Canary Worker

A `deploy_component` with `restart: true` or `restart: "rolling"` now checks its release before rolling it out. The first worker started on the release, the canary, is held out of traffic until it reports whether the deployed component loaded, and the rollout goes on only if it did. Each later replacement is checked the same way. When the node that received the deploy rejects the release, the deploy fails with `400`. The release it replaced is made live again, or, with nothing to go back to, the component fails closed on that node. A new `certification` field in the response reports the outcome, and says when a restarting deploy went out unchecked (`uncertified` or `unavailable`, as for a `package: file:<dir>` deploy). With `"rolling"`, each other node then certifies the release with a canary of its own, and a node that rejects it does not fail the deploy: the deploy's record ends `partial`, as [Following a Rolling Deploy to Every Node](#following-a-rolling-deploy-to-every-node) describes. A node running a version before 5.4.0 activates without a canary. A deploy that restarts nothing is not test-loaded. If its release throws when it loads, `get_status` reports the failure. See [Certifying a release in a canary worker](/reference/v5/operations-api/operations#certifying-a-release-in-a-canary-worker).

### Following a Rolling Deploy to Every Node

A certified `"rolling"` deploy now responds with `status: "rolling_out"`, and its deployment record follows the job that takes the release to the other nodes. The record names the job in `restart_job_id`, adds each node's outcome to its `peer_results` entry as `activation`, and ends `success` once every node has taken the release, or `partial` with `error.nodes` naming each node that did not. A job that fails before it reaches every node ends the record `partial`; one cut short by its node restarting, or unable to write the record's end, is settled at that node's next start from the job's own result. The record replicates, so any node answers `get_deployment` for it, where before only the node that received the deploy knew the job's outcome. `harper deploy restart=rolling` now waits on the record, prints each node's outcome, and exits non-zero when a node did not take the release or the wait runs out; `wait=false` skips the wait, and `wait_timeout=<ms>` bounds it. That wait needs `get_deployment`, which the role `harper deploy setup=true` creates now grants. A CI role written by hand with an `operations` list needs it added with `alter_role`, as does a trust policy scoped with `operations`; until then pass `wait=false`, or the wait is refused after the node you called has taken the release. See [Waiting for a rolling deploy](/reference/v5/cli/commands#waiting-for-a-rolling-deploy).

### Which Release Is Live on Each Node

The new `list_releases` operation lists, for each component, the release live on a node and the releases it keeps on disk to make live again, each with its `state` (`staged` or `kept`), `at` and `size`; `replicated: true` asks every node. `get_components` entries now carry the live release's `deployment_id`, `deployed_at`, when the deploy that made it live finished, and `restarted_at`, when that node last loaded it. See [`list_releases`](/reference/v5/operations-api/operations#list_releases).

### Where a Deploy Came From

Deployment records now carry `source`. A deploy made with a token from `exchange_oidc_token` records the claims the exchange verified, such as the repository, commit and workflow run, with `via: "oidc"`. Otherwise `via: "declared"` records what the client said, such as the commit of the checkout the `harper` CLI deployed. `list_deployments` takes `sha` to find the deploys of one commit. See [`get_deployment`](/reference/v5/operations-api/operations#get_deployment).

### Failed Deploy Payloads Expire

A failed deploy keeps its payload for retrying or debugging, but no longer forever: `deployment.payloadRetention.failedMaxAge` (default `7d`) and `failedMaxCount` (default `2`) bound how long, and how many per project, are kept. Each project's newest failed payload is always kept, and the record stays. See [`deployment.payloadRetention`](/reference/v5/configuration/options#deployment).

### Warning When a Declared Entry Point Matches Nothing

A deploy now warns when a `jsResource.files` or `graphqlSchema.files` pattern in the component's own config matches no file in the release, as a truncated payload would. The deploy still goes ahead. See [Declared entry points that matched nothing](/reference/v5/operations-api/operations#declared-entry-points-that-matched-nothing).

### Setting Up GitHub Actions Deploys

`harper deploy setup=true provider=github-actions` sets a cluster up so a GitHub Actions workflow can deploy with its OIDC identity token instead of a stored credential. It creates a deploy-only role and user, a trust policy matching the workflow's repository, branch and environment, and the repository's `HARPER_CLI_TARGET` variable. It checks the policy against the workflow file in the repository's checkout before it writes, where it can, and reads it back after. It only creates: running it again leaves the cluster and the variable as they are, a record that differs, or that someone deactivated or disabled, stops it before it writes, and a `HARPER_CLI_TARGET` that names another cluster is left in place. A policy with the same id that another super user creates in the moment before setup writes it is still overwritten. See [GitHub Actions deploys (OIDC)](/reference/v5/cli/commands#github-actions-deploys-oidc).

### A Rolling Restart Fails When a Node Did Not Restart

The job behind a replicated `restart_service` (and behind a `restart: "rolling"` deploy whose `certification` is `unavailable`) now ends `ERROR` when any other node did not restart, instead of `COMPLETE`. Its `message` names each node that failed or was skipped, and `result.replicated` holds one entry per other node in both outcomes, with an `error` key, not `message`, for a node that did not restart. A node whose restart failed or may still be running stops the roll, and the nodes after it are reported as skipped; a node whose write queue was full is retried after the others. See [`replicated`](/reference/v5/operations-api/operations#restart_service-replicated) ([harper#3498](https://github.com/HarperFast/harper/pull/3498)).

## Configuration

### Applying V8 Flags From the Configuration

The new `threads.v8Flags` setting takes a V8 flag, or a list of them, and applies them to the Harper process before its first worker thread starts, so every worker thread runs with them. It is for flags such as `--optimize-for-size`, which Node refuses in `NODE_OPTIONS` and which cannot be passed to a worker thread. It can also be set through `HARPER_SET_CONFIG` or `HARPER_CONFIG`. An entry must start with `--`; `set_configuration` refuses one that does not, and Harper stops at startup with an error naming the setting. Unlike the command line, this does not apply a flag's implied flags, so list them yourself (for example `--max-semi-space-size=1` alongside `--optimize-for-size`). A changed value takes effect when the process restarts (the `restart` operation, on each node); `restart_service` restarts only worker threads and does not apply it. Not applied under Bun. See [Applying V8 flags](/reference/v5/configuration/options#applying-v8-flags).

## Backups

### Restore Checks a Backup Before Deleting the Database

`restore_backup` no longer deletes a database before checking that the backup can be read. It first verifies the checksum of every database file in the backup, checks its transaction logs, opens each table file to confirm this version can read its format and compression, and, for a backup that captured blobs, checks that the blob snapshot is present. A backup that fails is refused and the database is left as it was (one an earlier restore left incomplete stays blocked); previously the restore deleted the database first and then failed, so a backup taken by a newer version, or one with a corrupt file, destroyed the database it was meant to restore. The check reads the whole backup once, so a restore takes longer, and an online restore keeps the database unavailable while it runs; it needs no extra disk space. A restore interrupted while it is still checking the backup leaves the destination's files and any preexisting incomplete-restore marker unchanged; a previously healthy database loads normally on the next start. Blob file contents are not checked. See [`restore_backup`](/reference/v5/backups/operations#restore_backup).

## Analytics

### The Harper Pro Profiler Samples in Short Windows

Harper Pro's CPU profiler used to sample every worker continuously, so each worker's `utilization` read about 70% at idle and every worker paid a stack walk every 50 ms. It now samples only for one `aggregatePeriod` before each capture: from application load until the second capture, two periods later, and then for one period in every thousand. Each `hdb_raw_analytics` entry whose `utilization` overlapped sampling carries a new `profiler-sampling` metric, so a consumer can set that sample aside. Ending each window also stops a wedged V8 profiler thread ([harper-pro#1021](https://github.com/HarperFast/harper-pro/issues/1021)). `analytics.profiling: false` still keeps the profiler off. See [`utilization` and the CPU profiler](/reference/v5/analytics/overview#utilization-and-the-cpu-profiler).

## Full-Text Search

### Tantivy 0.27 and Existing Index Rebuilds

Harper now uses `@harperfast/fulltext` 0.7.0 with Tantivy 0.27.0. Harper 5.3.1–5.3.4 ship fulltext 0.5.0. Existing 0.5.0 indexes using current field-based declarations, and prerelease 0.6 indexes, rebuild automatically from authoritative records. Harper 5.3.0 ships fulltext 0.3.0 and is outside this qualified procedure; validate that migration separately. Earlier beta declarations and indexes have no supported migration path. Plan for local full-text unavailability, disk headroom and possible retryable write failures while replay catches up. Stop old processes before starting the new version against the same storage; direct downgrade to fulltext 0.5.x is unsupported.

English stemming changes despite the unchanged `english@2` analyzer name: `added` now stems to `add` rather than `ad`. Matching and ranking can change. Query modes and schema options are unchanged; benchmark results from the wrapper do not establish application performance parity. Review representative searches and see [upgrading existing indexes](/reference/v5/full-text-search/overview#upgrading-existing-indexes) before restoring traffic.

### Paging and Search Work Limits

Full-text and autocomplete queries use the existing `limit` and `offset` paging options. Harper reads additional native batches when needed after filtering, so the initial native result window no longer silently cuts off eligible results. The new `storage.fullText.maxRawHitsPerRequest`, `storage.fullText.maxResultsPerRequest` and `storage.fullText.requestBudgetMilliseconds` settings bound fetched hits, retained results and execution time. Requests that exceed those budgets return an error. The `storage.fullText.runtime` section also provides process-wide native-capacity budgets; changes to those budgets require a full Harper process restart. Separate page requests run independently and can see changes to records or index contents.

See [Full-text query execution](/reference/v5/resources/query-optimization#full-text-search-work-and-paging) and [storage configuration](/reference/v5/configuration/options#storage) for limits, restart requirements and recovery guidance.

## Native Addons

### Pointer-Compression Runtimes Refuse Incompatible Native Addons

Free and Hobby tier clusters on Harper Fabric run on pointer-compression runtimes; other plans run a standard Node.js. On a Node.js build with V8 pointer compression, Harper now checks native addons before they load, in every thread. It refuses an addon that links V8's C++ API built for the standard ABI, which would otherwise load and then crash the process on first use. The refusal is an `IncompatibleNativeAddonError` that names the file, its package and the fixes.

These still load as before:

- Node-API addons;
- addons that node-gyp built under the running Node.js, load from the package's `build/` directory, and meet the `config.gypi` and binary-age checks in the reference;
- packages marked with `.pointer-compression-build`.

Standard Node.js builds are unchanged. See [Native Addons on Pointer-Compression Runtimes](/reference/v5/components/module-loading#native-addons-on-pointer-compression-runtimes).

## Security

### An Operations API Source Allowlist for a Fronting Proxy

`set_network_access` stores a list of allowed source CIDRs for the operations API in the `system.hdb_network_access` table, which replicates like users and roles, and `get_network_access` reads it; both are `super_user` only. Harper publishes the list as `allowedSources` in the metadata file of each operations API Unix domain socket (`tls.unixDomainSockets` with `operationsApi.network.securePort`), and rewrites it on each node the change replicates to. A proxy that reads that file, such as Harper Fabric's, admits only the listed addresses. Harper does not enforce the list on its own listeners. Setting a non-empty list that excludes the request's source address, or when Harper cannot tell that address, fails with `409` unless it passes `force: true`; on Node.js the local CLI, over the operations domain socket, is never checked. See [Network Access](/reference/v5/operations-api/operations#network-access) ([harper#3358](https://github.com/HarperFast/harper/issues/3358)).

## Container Images

### Harper Pro Images Run on jemalloc

The `harperfast/harper-pro` image, its pointer-compression variant (the `-pc` tags) and the GPU image (`harperfast/harper-pro-gpu`) now install the distribution's jemalloc package (`libjemalloc2`, version 5.3.0) and set `LD_PRELOAD=libjemalloc.so.2`, so every process in the container allocates memory with jemalloc instead of glibc malloc. jemalloc runs with its default settings; the images set no `MALLOC_CONF`. RocksDB's allocation pattern fragments glibc malloc's heap. In tests on 5.3.4, jemalloc used about 5% less memory (RSS) under a 3 GB memory limit and grew it about half as fast. In short runs without a memory limit it gave YCSB workload A (half reads, half updates) about 5% more throughput, with no measurable difference in peak memory. Expect the memory saving under a memory limit, and not on every workload.

- To run a container on glibc malloc, set `LD_PRELOAD` to an empty value: `docker run -e LD_PRELOAD= harperfast/harper-pro`.
- A deployment that sets its own `LD_PRELOAD`, for example to load an instrumentation library, replaces jemalloc. To keep both, list both: `LD_PRELOAD="libjemalloc.so.2 /path/to/other.so"`.
- glibc malloc settings such as `MALLOC_ARENA_MAX` have no effect while jemalloc is preloaded.

The OpenShift image (`harperfast/harper-pro-openshift`) and the open source `harperfast/harper` image are unchanged and still use glibc malloc. See [harper-pro#1132](https://github.com/HarperFast/harper-pro/pull/1132).
